# Waygate 0.2.0 release notes

Changes since `v0.1.4` (`39d724776d1abb11f7ed2c28328674daaa6a9918`): commits `fda693a` (gateway image modes, durable agent-token rotation), `682161a` (deletion finalization and operational runtime fixes) and the client tunnel-settings/PSK/traffic-status change. Status: **candidate for release, not deployed to production.** Nothing in this section is published until the reviewed release commit is tagged `v0.2.0`, the tag-triggered Docker Build & Push run passes, and a maintainer attaches the wheel to a GitHub Release. The existing `v0.1.4` tag and its artifacts are not replaced.

Version map: the root `waygate` distribution (`pyproject.toml`), runtime `waygate.__version__`, root `uv.lock` and the packaged Kolla registry default `waygate_image_tag` are `0.2.0`. `waygate-sdk` is independently versioned, stays `0.1.2`, and is not part of this release. The Kolla source-build checkout `waygate_source_version` stays pinned to the existing immutable commit `1c59b5e86d3c3c1b9d3397b38301ee9bc401cf03`; that commit is not the 0.2.0 source, so source-mode operators must explicitly select the reviewed release commit.

## New in 0.2.0: client tunnel settings, generated PSK and traffic status

- Client create and `PATCH` accept per-client DNS (at most two addresses, normalized), nullable MTU (576–9000) and PersistentKeepalive (0–65535, default 25; `0` disables it). `PATCH` keeps omitted values, clears DNS/MTU with `null`, and rejects `null` for `enabled`/`persistent_keepalive`. The rendered `.conf` includes these values. Gateways do not push settings to client devices: after a change, the user must re-download and reimport the `.conf`.
- Every newly issued client gets its own random WireGuard preshared key, stored encrypted and delivered to the gateway agent's desired state and to that client's `.conf`. Existing clients are not rotated: their private key and PSK state (including no PSK) are unchanged. If a stored PSK ciphertext cannot be decrypted, `.conf` download fails and the agent desired state omits that peer; the PSK is never silently dropped.
- `GET /v1/servers/{server_id}/clients` joins one Redis agent report by public key and adds `psk_enabled`, `mtu`, `persistent_keepalive`, `last_reported_at`, `last_handshake_at` and gateway-perspective `rx_bytes`/`tx_bytes`. `online` is true only for an enabled client whose report and handshake are both within 120 seconds. Redis reports (TTL 5 minutes) are observational, not durable usage history. List responses never include plaintext keys. Afterglow maps gateway TX to client RX and computes rates only from successive real reports.
- Passphrase-wrapped export/import carries DNS/MTU/keepalive and the PSK when one exists. Imported settings are revalidated, and older bundles without a PSK import without one.
- API compatibility: response fields are additive. Client create/update bodies now reject unknown fields (422), require strict integers, and reject DNS lists with more than two addresses. Callers that send only the 0.1.4 fields remain accepted, subject to the stricter DNS validation.

## Included from post-0.1.4 commits `fda693a` and `682161a`

- Gateway installation supports `cloud-init` (default) and `prebuilt`, snapshotted per server. Prebuilt mode requires a public/community Glance image with `waygate_agent=prebuilt`. Both modes use the same agent and persist its configuration separately from its executable. The 0.2.0 Kolla role renders `waygate_agent_install_mode`; the installed 0.1.4 role did not.
- Tenant owners can request `POST /v1/servers/{server_id}/agent-token/rotate`. The agent fsyncs both the replacement file and its directory before using the pending bearer, and checks directory durability on later loads. First successful pending-bearer authentication conditionally promotes the persisted ciphertext and invalidates the old bearer. Repeated/concurrent requests retain an existing pending rotation. Issuance, rotation and revocation require durable DB commits; authentication ignores obsolete Redis credential entries and fails closed when the DB is unavailable. Redis remains a status cache only.
- Gateway WireGuard configuration assigns the first usable tunnel address. Ubuntu 24.04 amd64 images can be built through local QEMU or native OpenStack; provisioning removes inherited SSH authorized keys before snapshotting.
- Operational fixes use Redis 5.0.0's async `close()` for API shutdown and cutover, and correctly consume the asynchronous key scan during cutover verification. Discovery and rate limiting share trusted proxy interpretation; configure `waygate_trusted_proxies` with only actual load balancer addresses so public HTTPS links remain HTTPS without trusting arbitrary forwarded headers.
- Gateway deletion finalizes a durable `DELETED` tombstone only after cloud cleanup, cascades client disable/soft-delete and key erasure, and removes cleaned attachment records. The worker verifies terminal state instead of treating an API-hidden row as proof of completion. Parent-row admission locks prevent client/attachment creation from racing past delete enqueue; existing historical verification rows require bounded repair only after independent cloud-resource absence checks.
- Floating-IP discovery/deletion failures keep delete jobs retryable without losing the FIP association. Detach rejects still-creating attachments, client mutation serializes with server deletion, and a client removed during creation returns 404 rather than 500.

## Upgrade prerequisites

- Apply the additive, checksum-verified migrations `002_agent_install_mode_and_token_rotation.sql` (if not already applied) and `003_client_tunnel_settings.sql` before starting 0.2.0 API/worker processes. Migration 002 defaults existing servers to `cloud-init`; migration 003 adds nullable `mtu` and non-null `persistent_keepalive` (default 25) to existing client rows. 0.2.0 code must not run against a pre-003 schema. In Kolla, migrations run only in `kolla-ansible deploy --tags waygate` (bootstrap), not `reconfigure`. Back up the database and keep the previous image/configuration references for rollback.
- Set Kolla `waygate_callback_base_url` explicitly to the VM-reachable public API URL. A separately configured `waygate_public_endpoint_url` does not override the callback default. The service account needs a role with resource-creation permissions in each project it provisions; with zero-root-disk flavors, Nova's default `zero_disk_flavor` policy requires that role to be `admin`.
- The gateway agent source is unchanged from the `fda693a` revision (agent directory digest `fe71034dec6a46701b1ae284a0a824058f10ee4a7c97d7aa981f1152e48f95a3`). Existing gateways and the existing prebuilt Glance image `waygate-gateway:0.1.4-ubuntu-24.04` (`bcb724e6-0893-4546-b891-8dc143c63489`) therefore need no rebuild; that image keeps its 0.1.4 name and metadata. A new image build from 0.2.0 source would be named `waygate-gateway:0.2.0-ubuntu-24.04` by default and would be a new Glance image, not a replacement.
- Afterglow's client settings and traffic display rely on the 0.2.0 response fields; 0.1.4 responses omit them.

## Evidence and production boundary

Pre-0.2.0 production evidence (historical; the package still reported 0.1.4): amd64/arm64 API and worker image builds and runtime feature smoke passed, and `ARCHITECTURE.md` records the QEMU and native OpenStack image build/fresh-boot evidence. The DMSLAB Kolla rollout of `fda693a` passed a full deployed cloud-init lifecycle, including probe-VM tunnel/SNAT traffic, token rotation and deletion. `ARCHITECTURE.md` records the digests, commands and the access changes required. The remediation commit `682161a` was then deployed by digest with the controller HAProxy trust list. A deployed lifecycle on a fresh VLAN 3505 network passed probe tunnel/SNAT traffic and proved the deletion cascade (`DELETED`, erased client keys, removed attachment, completed job).

2026-09-26 operator-only image cutover: the active DMSLAB `waygate.image` policy selects the already-built, community-visible prebuilt Glance image `bcb724e6-0893-4546-b891-8dc143c63489`. The installed 0.1.4 Kolla role needed the missing `agent_install_mode` defaults/template delivery line. Globals request `prebuilt` without changing the deployed API/worker digests. A fresh production gateway reached ACTIVE and reported `agent_source=prebuilt`; Nova used that image and the boot console showed no package install. The disposable gateway was deleted and existing cloud-init `test-wg` remained ACTIVE/unchanged. Rollback inputs (globals, role template/defaults, policy, inventory) are root-only at `/etc/kolla/afterglow-release-backups/waygate-prebuilt-20260926T160317Z/`.

Client-feature evidence (local and isolated data plane only): isolated MariaDB migration 003 passed. Also passed: authenticated BFF issue/edit/config/QR, a passphrase-wrapped export/import that preserved the exact client private key and PSK, and an Ubuntu kernel WireGuard PSK tunnel with successful pings and real agent byte counters. The browser displayed actual report-derived RX/TX. Full serial and four-worker Waygate suites, the SDK suite, and x86 API/worker container builds passed on the pre-release source. `ARCHITECTURE.md` has details. **No client-feature source, 0.2.0 image or 0.2.0 Kolla role has been deployed to DMSLAB**, and no deployed Nova-provisioned lifecycle has exercised generated PSKs or client settings.

Open issues, not changed in this release: requests without `X-Project-Id` operate in the caller's default Keystone project rather than the token's scope. The per-request system-admin lookup ignores `waygate.os_interface`; it used the public Keystone URL and stalled about 30 seconds on one controller before failing closed.

## Maintainer validation and manual publication (not performed by this release preparation)

1. On the reviewed release commit, stamp and check the architecture document (`python3 scripts/check_architecture.py --stamp --summary "..."`, `python3 scripts/check_architecture.py`, and after staging only intended files `python3 scripts/check_architecture.py --staged`). Run `uv sync --extra service --extra dev --frozen`, `uv run pytest tests`, `uv run pytest tests -n 4 --dist worksteal`, and `uv run ruff check .`. In `sdk/`, run `uv sync --all-extras --frozen`, `uv run pytest`, and `uv run ruff check .`. `tests/test_kolla_assets.py` builds the wheel and checks its Kolla shared-data payload against the manifest version. These are not live proof.
2. Land the release commit, create the annotated tag on that exact commit (`git tag -a v0.2.0 -m 'Waygate 0.2.0'`), and push the branch and then the tag (`git push origin <release-branch>`, `git push origin v0.2.0`). Wait for the tag-triggered Docker Build & Push run to pass and confirm the `0.2.0` tags and digests for `ghcr.io/openstack-afterglow/waygate-api` and `ghcr.io/openstack-afterglow/waygate-worker`. Do not move the tag after publication. CI image publication is not a production deployment.
3. From the tagged source, run `uv build --wheel --out-dir dist/0.2.0`. Inspect `waygate-0.2.0-py3-none-any.whl` metadata and its `share/kolla-ansible/ansible/roles/waygate` payload (`waygate_image_tag: "0.2.0"`), and verify the artifact comes from the tagged commit. The workflow does **not** create a GitHub Release or attach a wheel. Run `gh release create v0.2.0 dist/0.2.0/waygate-0.2.0-py3-none-any.whl --verify-tag --title 'Waygate 0.2.0' --notes-file RELEASE_NOTES.md` and confirm the wheel asset is attached. This is a manual GitHub asset upload, not a PyPI publish.
4. Only after publication can Afterglow's Kolla operator lock resolve `v0.2.0`. A production rollout is a separate, explicitly authorized operation. It must back up the DB, pin the published amd64 digests, and run `deploy --tags waygate` so that migration 003 is applied. After that, it must run the opt-in live lifecycle, including client settings/PSK data-plane checks.

# Waygate 0.1.4 release notes

Historical record of the published `v0.1.4` release (tag commit `39d724776d1abb11f7ed2c28328674daaa6a9918`), kept as written at release preparation. Its candidate-status and live-verification statements describe 0.1.4 only; see the 0.2.0 section above for later evidence.

Changes since `v0.1.2` (`0257ac17bb2baafc684aa065ee879fd50c324ef1`). This is a release candidate until the reviewed commit is tagged, the gates pass, and artifacts are published.

## Changes

- Unified the Kolla-Ansible Waygate role into the root `waygate` distribution as wheel shared data at `share/kolla-ansible/ansible/roles/waygate`. Kolla-Ansible is not a runtime or wheel dependency. The service can still be installed with the `service` extra; the SDK remains a separately versioned distribution (`waygate-sdk` 0.1.2).
- Relaxed the root Python requirement to `>=3.11` for the Kolla control node, while CI and the runtime image use Python 3.12.
- API and worker startup now reject missing or loopback/unspecified `waygate.callback_base_url` rather than silently substituting an internal name that a gateway VM cannot reach. The provisioning path validates the public callback before creating cloud resources. Operators must supply a reachable public URL.
- Network attachment now creates a Neutron port constrained to the selected subnet (`fixed_ips`), attaches that port by ID to the Nova VM, and records it for detach/rollback. Failed port cleanup retains an `ERROR` attachment for recovery; the optional live lifecycle covers create, attach, detach, and delete but has not been run for this release candidate.
- CI runs the service suite with four pytest-xdist workers. Push/tag/dispatch image publication waits for the reusable service-and-SDK checks; a PR builds images without publishing them, while PR CI runs separately. The contract checks guard publish gating, runner use, unsafe workflow expressions, and trigger shape. A release tag produces the `0.1.4` semver image tags for both `ghcr.io/openstack-afterglow/waygate-api` and `ghcr.io/openstack-afterglow/waygate-worker` after the gate passes.

## Compatibility and operational limits

The root manifest, runtime `__version__`, root `uv.lock`, and packaged Kolla registry-image default are 0.1.4. The source-build checkout remains pinned to its existing immutable commit `1c59b5e86d3c3c1b9d3397b38301ee9bc401cf03`; it is not a synonym for the 0.1.4 release. Source-mode operators must explicitly select a reviewed, immutable release commit if they need the new code. The role's registry refs still accept full SHA-256 digests or version tags, reject `latest`, and do not change reference validation. Pin both deployed images to their published digests for immutable deployments; do not assume a tag is immutable.

No live OpenStack/MariaDB/Redis/gateway VM lifecycle has been verified for this candidate. The opt-in lifecycle test requires an authorized deployment, a Keystone token, network and optional subnet IDs; it has not established data-plane connectivity. `/v1/health` is only a process health check. There is no OpenSpec tree in this repository and no OpenSpec artifact to synchronize.
